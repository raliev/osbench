# Вопросы, которые можно задать стенду osbench

Каждый вопрос сформулирован так, как его задаёт менеджер интернет-магазина, и сведён
к конкретным осям параметров сценария и к одной первичной метрике. Все перечисленные
параметры существуют в `osbench/config/schema.py` и реально читаются движком.

Протокол ответа одинаков для всех вопросов: 30 сидов на ячейку, общие случайные числа
(один сид → один и тот же мир и один и тот же поток заказов для всех вариантов),
парная разность по сиду, 95 % доверительный интервал по t-распределению и бутстрепу,
поправка Холма на множественные сравнения внутри вопроса.

Статус: **✅ исследовано** — проведён полный эксперимент, см. `papers/`.
**⚠️ проверено, эффект мал** — быстрый зонд показал эффект на уровне шума в текущих сценариях.

## A. Стоит ли вкладываться в IT-функцию

### A1. Нужно ли онлайн-резервирование товара? ✅

> «Если OMS будет резервировать остаток в момент заказа, а не на сборке — сколько заказов
> мы перестанем отменять и во что это обойдётся?»

| | |
|---|---|
| Оси | `reservation.enabled: [true, false]` × нагрузка сети ρ (контеншн) |
| Первичная метрика | `lost_sales_rate` (не `total_cost_per_order` — он на 85 % COGS) |
| Пояснительные | `shortage_rate_pick`, `promise_hit_rate`, `lateness_days_p90` |
| Результат | см. `papers/study2_ru.md`, исследование C: рычаг fill rate с платой по on-time, работает только при ρ ≳ 0,6 |

### A2. Нужен ли ATP с учётом будущих приходов?

> «Стоит ли показывать на карточке товар, которого ещё нет, но он приедет послезавтра?»

| | |
|---|---|
| Оси | `atp.method: [on_hand_only, basic, cumulative]` × `atp.horizon_days: [3, 7, 14]` |
| Первичная метрика | `total_cost_per_order` |
| Пояснительные | `promise_rejection_rate`, `shortage_rate_checkout` против `promise_hit_rate`, `lateness_days_p90` |
| Суть | цена оптимизма в промисе |

### A3. Сколько стоит один процент точности учёта остатков? ⚠️

> «Окупится ли циклическая инвентаризация или новый WMS?»

| | |
|---|---|
| Оси | `inventory_accuracy.accuracy: [1.0, 0.99, 0.98, 0.95]` × `reservation.enabled` |
| Первичная метрика | наклон `total_cost_per_order` по точности |
| Пояснительные | `shortage_rate_pick`, `lines_cancelled_by_stage.pick` |

Быстрый зонд на `demo_scarce` показал эффект ниже уровня шума: ошибка учёта
(в среднем 2 единицы на приход) пренебрежимо мала относительно партий пополнения
(MOQ 40 и выше), а расхождение сверяется на первой же сборке. Чтобы вопрос стал
содержательным, нужен сценарий с мелкими частыми приходами и длинным хвостом SKU —
или более крупный `inventory_accuracy.error_mean`.

## B. Насколько умным должен быть алгоритм

### B1. Когда sourcing-алгоритм окупается, а когда нет? ✅

> «У нас сейчас "ближайший склад". Что мы теряем и при каких условиях?»

| | |
|---|---|
| Оси | политики `[random, nearest, cheapest_myopic, weighted_score, dtlp_bidprice]` × загрузка сети ρ = спрос / мощность |
| Первичная метрика | `total_cost_per_order` относительно `nearest` |
| Пояснительные | `promise_hit_rate`, `penalty_cost`, `fc_utilization` |
| Результат | см. `papers/study_ru.md`, исследование A |

### B2. Окупается ли подбор весов, а не просто внедрение weighted score?

> «Нам нужен дата-сайентист или хватит здравого смысла в настройках?»

| | |
|---|---|
| Оси | `weighted_score` (дефолт) против `weighted_score_tuned` (команда `osbench tune` на сидах 0–9), тест на сидах 15–44 |
| Второй разрез | веса, настроенные при ρ = 0,8, прогоняются при ρ = 1,1 и при выпадении склада |
| Первичная метрика | `total_cost_per_order` |
| Суть | переживёт ли настройка чёрную пятницу |

### B3. Окупается ли тяжёлая LP-политика с прогнозом?

> «dtlp стоит в разы больше вычислений. Что он даёт сверх настроенного weighted score?»

| | |
|---|---|
| Оси | пара `weighted_score_tuned` × `dtlp_bidprice` в нескольких режимах нагрузки |
| Первичная метрика | `total_cost_per_order` |
| Пояснительные | `decision_time_ms_p99`, `gap_to_hindsight` |

### B4. Сколько денег лежит на столе в принципе?

| | |
|---|---|
| Метрика | `gap_to_hindsight` текущей политики — верхняя граница любой оптимизации sourcing |
| Смысл | если разрыв 3 %, разговор про RL можно закрывать |

## C. Обещание клиенту

### C1. Что даёт +1 / +2 дня к обещанному сроку? ✅

> «Если перестать обещать завтра и начать обещать послезавтра — сколько сэкономим
> и сколько клиентов потеряем?»

| | |
|---|---|
| Оси | `promise.buffer_days: [0, 1, 2, 3]` × `deferral.mode: [none, wait_for_receipt]` × `promise.p_accept_promise: [1.0, 0.6]` |
| Первичная метрика | `lost_sales_rate` |
| Пояснительные | `promise_hit_rate`, `promise_rejection_rate`, `shipping_cost_per_order` |
| Обязательное условие | `p_accept_promise < 1`, иначе длинный промис выигрывает бесплатно |
| Результат | см. `papers/study_ru.md`, исследование B |

### C2. Стоит ли дать заказу подождать прихода товара вместо разбиения? ✅

| | |
|---|---|
| Оси | `deferral.mode: [none, wait_for_receipt, wait_to_consolidate]` × `deferral.safety_margin_days` × разброс поставок `suppliers[].lead_time_std_days` |
| Первичная метрика | `lost_sales_rate` и `total_cost_per_order` |
| Пояснительные | `deferred_share`, `split_rate`, `promise_hit_rate` |
| Ожидание | при росте разброса lead time стратегия должна переворачиваться |

### C3. Что лучше при нехватке — отправить часть или отменить заказ целиком?

| | |
|---|---|
| Оси | `shortage.p_partial_ship: [0, 0.5, 1.0]` × `shortage.penalty_post_order: [4, 8, 16]` |
| Первичная метрика | `total_cost_per_order` |
| Смысл | точка безубыточности по «цене разочарования клиента» |

## D. Запас против софта

### D1. Что дешевле — ещё неделя запаса или более умный sourcing? ⚠️

| | |
|---|---|
| Оси | `initial_cover_days: [6, 10, 16, 24, 30]` × политика |
| Первичная метрика | эквивалент: на сколько дней покрытия тянет переход `nearest → weighted_score` |

Ограничение, найденное при зондировании: `initial_cover_days` задаёт только стартовый
запас. Политика пополнения `base_stock` за два цикла пересмотра выводит сеть в свой
стационарный уровень, поэтому на горизонте 45–90 дней начальное покрытие влияет слабо
и немонотонно. Чтобы ответить на вопрос честно, нужно варьировать стационарный уровень
(`ReplenishmentPolicyConfig.S_overshoot` / `safety_days` / `service_level`), а он сейчас
не выведен в оси sweep. Это задача на доработку.

### D2. Сколько мы теряем на рассогласовании закупки и sourcing?

| | |
|---|---|
| Оси | `replenishment: [base_stock, forecast_driven, network_allocation]` × политика sourcing |
| Первичная метрика | `total_cost_per_order` |
| Смысл | интересна матрица взаимодействия, а не главные эффекты |

### D3. Насколько политика устойчива к выпадению склада? ✅

| | |
|---|---|
| Оси | `shocks.warehouse_outage_days: [0, 3, 7]` × нагрузка ρ × политика |
| Первичная метрика | деградация `promise_hit_rate` относительно спокойного прогона |
| Пояснительные | `total_cost_per_order`, посуточная кривая восстановления |
| Результат | см. `papers/study2_ru.md`, исследование D: обрыв устойчивости при ρ≈0,8, решает запас мощности, а не политика |

## Что нужно доработать в стенде

1. **Поправка на множественные сравнения.** `osbench compare` считает парные ДИ,
   но не корректирует их при сетке «политика × метрика × ячейка». Нужен Холм или
   Бенджамини — Хохберг.
2. **Параметры политик как оси sweep.** Сейчас в YAML эксперимента `replenishment`
   задаётся только именем. Без `S_overshoot` / `service_level` в осях вопрос D1
   не отвечается корректно.
3. **Отсутствующие метрики.** Нет `splits_avoided_by_deferral` (нужна для C2),
   `fc_utilization` и `inventory_days` (объясняют *почему* в ячейке побеждает
   другая политика).

## Новые механизмы движка (готовы к экспериментам)

- **A4. Латентность синхронизации остатков (`inventory_sync`, разд. 2.12).** OMS видит
  снимок WMS с опозданием. Оси: `inventory_sync.mode` / `lag_minutes` / `period_minutes`
  × резервирование × нагрузка ρ. Метрики: `oms_wms_divergence_units`,
  `shortage_pick_stale_snapshot_share`. Гипотеза: порог контеншена, выше которого
  резервирование окупается, сдвигается влево пропорционально лагу.
- **A5. Отмены клиентов (`demand.cancel_rate`).** Главный честный аргумент против раннего
  связывания: резерв держит ходовую единицу под заказ, который клиент отменит. Оси:
  `cancel_rate` × резервирование × ρ. Метрика: `customer_cancel_rate`, `lost_sales_rate`.
- **E1. Перемещения между складами (`transfers`, разд. 2.13).** Главный конкурент умного
  sourcing: товар возят заранее, а не заказ издалека. Политики `threshold_balance`,
  `pull_base_stock`. Метрики: `transfer_cost` (входит в `total_cost`), `transfer_share`,
  `ping_pong_units`. Стык с D3: восстанавливается ли сеть после выпадения склада, если
  включить ребаланс.
- **E2. Стохастический lead time (`suppliers[].lead_time_std_days`).** Теперь реально
  читается движком (лог-нормаль, поток `supplier_leadtime`). Делает отложенный sourcing
  (C2) рискованнее — прямое расширение исследования B.
