# Техническое задание: симуляционный стенд выбора склада (order sourcing) для e-commerce

Nov 4, 2026 · @Rauf

## 1. Цель и границы

Стенд — открытый воспроизводимый бенчмарк для сравнения алгоритмов выбора склада под заказ (order sourcing) в сети e-commerce. Позиционирование — benchmark/testbed-статья: главный вклад не новый алгоритм, а параметризуемый дискретно-событийный симулятор с общими случайными числами (CRN) и строгим протоколом сравнения.

***Исследовательские вопросы статьи***

- *RQ1. Окупает ли прогноз спроса в тяжёлых dual-LP политиках (DTLP) свою погрешность по сравнению с лёгкой взвешенной оценкой, настроенной байесовской оптимизацией?*
- *RQ2. Насколько качество sourcing зависит от согласованности с политикой пополнения (`base_stock` против `network_allocation`)?*
- *RQ3. Каков компромисс между задержкой решения (p99 мс на заказ) и снижением логистических затрат в масштабе крупной сети?*
- *RQ4. Кто робастнее при стохастических транзитных временах и сдвиге спроса — правила, LP или обученные политики?*
- *RQ5. Сколько стоит день запаса* в промисе: как буфер срока и отложенный sourcing меняют разбиения, стоимость, точность план-факта и отказы клиентов из-за длинного срока?

Целевые площадки: NeurIPS Datasets & Benchmarks (стенд, Gymnasium-интерфейс, протокол RL против OR) либо EJOR / Computers & Operations Research (управленческие выводы по RQ1–RQ2); JOSS — для самого пакета.

**Что делает стенд**

- Генерирует сценарий (сеть, товары, поставщики, спрос) из YAML-конфига и сида.
- Прогоняет заданный горизонт (по умолчанию 90 дней) с любой подключённой политикой sourcing и любой политикой пополнения.
- Пишет полный журнал событий и агрегаты, считает метрики, строит парные доверительные интервалы между политиками.
- Запускается из консоли; визуализация — отдельная команда поверх сохранённых результатов (статические HTML-отчёты и интерактивный просмотр прогона).

**Границы (не делаем в v1)**

- Внутрискладские процессы (батчинг, сборщики) — склад моделируется дневной пропускной способностью.
- Внутрисетевая логистика сверх одного перевозчика: несколько служб доставки, собственный транспорт — v2.
- Ценообразование, возвраты, промо, персонализация.
- Last-mile маршрутизация.

**Ключевые решения**

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Тип симуляции | Дискретно-событийная, один поток, собственный цикл событий (без SimPy) | Проще контролировать RNG-потоки и производительность |
| Единица времени | Минуты, целые числа | Детерминизм сортировки событий |
| Язык | Python 3.11+, NumPy, pandas, pydantic; LP — HiGHS через scipy/pulp; RL — PyTorch + Gymnasium-обёртка | Доступность для рецензентов и студентов |
| Масштаб v1 | До 20 складов, 10 000 SKU, 50 регионов, 1 млн заказов за прогон | Укладывается в минуты на ноутбуке |
| Открытость | MIT-лицензия, код + конфиги + сиды + эталонные результаты в репозитории | Это главный пробел в найденной литературе |

## 2. Модель мира

Мир состоит из шести сущностей: регионы с клиентами, склады, почта, товары, поставщики, заказы. Все параметры задаются в YAML; всё случайное генерируется из именованных RNG-потоков (раздел 6).

### 2.1 География и клиенты

- По умолчанию реальные координаты (lat/lon, расстояние по гаверсинусу): центроиды и население агломераций из открытых данных (US Census, Eurostat или Росстат). Синтетическая плоскость 1000 × 1000 км — только для пресетов tiny/small и юнит-тестов.
- Регионы: N точек-центроидов с населением (вес спроса). Генератор: равномерно, кластерами (городские агломерации) или из CSV.
- Клиент заказа = регион + случайное смещение внутри радиуса региона. Расстояние считается от склада до точки клиента.

### 2.2 Склады (fulfillment centers)

| Параметр | Тип | Пример |
| --- | --- | --- |
| Координаты | точка | (120, 340) |
| Пропускная способность | строк заказа в день | 5 000 |
| Cut-off | время дня, после которого заказ уходит завтра | 16:00 |
| Стоимость обработки | ₽ за строку заказа | 25 |
| Стоимость хранения | ₽ за единицу в день | 0,4 |
| Ёмкость хранения | единиц (опционально) | 200 000 |
| Ассортимент | подмножество SKU, которые склад вообще может хранить | 60 % |

Заказы сверх дневной мощности встают в очередь на следующий день и отражаются в метрике опозданий.

### 2.3 Почта (доставка)

Базовый режим — предсказуемая почта: время и цена задаются расстоянием и зоной. Для пары «склад → клиент» считаются:

- Зона = ближайшая граница по таблице расстояний, например 0–50 / 50–300 / 300–1000 / 1000+ км.
- Цена = фикс. ставка зоны + ставка за кг × вес посылки (+ опционально за объём), в условных единицах; крутизна роста по зонам — параметр сценария (пологая / средняя / крутая). Реальные сетки операторов и способ доставки не моделируются: важно лишь, что цена и срок различаются между складами-кандидатами.
- Время = целое число дней по зоне (1 / 2 / 4 / 7) + 1 день, если упаковка завершилась после cut-off. Sourcing планирует отгрузку по квантилю времени обработки (planning\_quantile, по умолчанию p80), а фактическая дата отгрузки определяется моментом завершения pack: заказ, принятый в 15:30 при cut-off 16:00 и собранный к 16:15, уезжает завтра, и этот день относится на внутреннюю задержку склада, а не на перевозчика.
- `delivery_noise_days` — распределение задержки сверх тарифного срока (0 / геометрическое / эмпирическое по зоне), свой RNG-поток. В части сценариев статьи шум обязателен: без него задача для LP и правил слишком стерильна, а ценность динамического sourcing проявляется именно при сбоях логистики.
- Мощность перевозчика по складу: лимит посылок в день (опционально); при превышении посылка отправляется на следующий день.

Разбиение заказа на несколько складов = несколько посылок, каждая со своей ценой и сроком. Срок заказа = максимум по посылкам.

Консолидация (опция `consolidation`): посылки одного заказа с разных складов сходятся в хабе; срок заказа = максимум по плечам «склад → хаб» плюс плечо «хаб → клиент», цена = сумма плеч со скидкой за одну последнюю милю. По умолчанию выключена, включается в сценарии «сеть с кросс-докингом», чтобы штраф за разбиение не был упрощением в пользу авторов.

### 2.4 Товары (SKU)

- K SKU с категорией, весом, объёмом, себестоимостью, ценой продажи, маржой.
- Популярность по закону Ципфа (параметр `zipf_s`, по умолчанию 1,1) — «длинный хвост» нужен, чтобы разбиения и дефициты возникали естественно.
- Корреляция спроса между регионами и категориями — через матрицу весов «регион × категория».

### 2.5 Поставщики

У каждого SKU один или несколько поставщиков; у поставщика:

| Параметр | Смысл |
| --- | --- |
| `lead_time` | распределение срока поставки (детерминированный, равномерный или лог-нормальный) — отдельный RNG-поток |
| `moq` | минимальный размер заказа |
| `price(q)` | цена с объёмными скидками |
| `fill_rate` | доля фактически поставленного от заказанного |
| `capacity_per_period` | лимит отгрузки в неделю на всех клиентов-складов |
| `serves` | какие склады обслуживает и с какой наценкой за дальность |

Поставка приходит на склад событием `receipt`; до прихода запас числится как «в пути» (on-order) и виден политикам пополнения и, по флагу, политикам sourcing.

### 2.6 Заказы и спрос

- Поток заказов — неоднородный пуассоновский процесс: базовая интенсивность × сезонная кривая (день года) × недельный профиль × суточный профиль × вес региона.
- Сценарные шоки: пиковые дни (например, ×4 на 3 дня), сдвиг спроса между регионами, выпадение склада на M дней — задаются списком событий в конфиге.
- Состав заказа: число строк \~ геометрическое (среднее настраивается, обычно 1,6), SKU по Ципфу с поправкой на категорию региона, количество \~ 1–3.
- Delivery promise — по зоне доставки (например, 2 дня до 50 км, 3 дня до 300 км, 5 дней дальше); единый промис на всю сеть — только как опция, иначе штрафы за опоздание искажаются между локальными и дальними заказами. Политика видит промис; факт сравнивается с ним в метриках.
- Калибровка генератора по открытым данным: параметры Ципфа, размер корзины, недельный и суточный профили подбираются по датасету Olist (есть геокоды) или JD.com (MSOM Data Challenge); отчёт о калибровке (QQ-графики, сравнение моментов) входит в репозиторий, чтобы снять вопрос «похож ли синтетический спрос на реальный».

### 2.7 Машина состояний заказа

Заказ проходит двенадцать состояний; время ожидания в каждом задаётся распределением из конфига (поток `process_times`), а три точки, где товара может не оказаться, ведут в отдельные стратегии (2.9).

Левая колонка — основной путь заказа сверху вниз; правая — три стратегии при нехватке, каждая либо возвращает заказ на путь (частично, с заменой, пере-сорсингом), либо уводит в «Отменён». Без резервирования шаг «Резерв» пропускается, и конфликты всплывают на развилке «Физически есть?».

| Состояние | Что происходит | Время ожидания (по умолчанию) |
| --- | --- | --- |
| Создан → ATP-проверка | клиент на кассе, сеть проверяет ATP по строкам (2.8), выдаётся промис (2.10) | 0 |
| Ожидает sourcing | задержка до запуска sourcing: батчинг, антифрод, оплата | равномерное 5–30 мин |
| Отложен по SLA | политика вернула Defer: ждёт прихода товара или дедлайна в пределах запаса по сроку (2.10) | 0 при `deferral: none`, иначе до события |
| Решение sourcing | вызов политики; в модельном времени 0, реальное время логируется | 0 |
| Резерв | списание из ATP, если резервирование включено | 0 |
| Очередь обработки склада | ждёт начала сборки с учётом cut-off и дневной мощности | лог-нормальное, медиана 2 ч, не раньше открытия смены |
| Pick | сборка строк; здесь сверяется физический остаток | лог-нормальное, медиана 10 мин + 3 мин на строку |
| Pack | упаковка посылки | лог-нормальное, медиана 5 мин |
| Отгружен → Доставлен | тарифный срок зоны плюс шум (2.3); готовый заказ уходит сразу | по зоне |

Терминальные состояния: «Доставлен» (возможно, с отменёнными строками — тогда заказ считается частично выполненным) и «Отменён». Каждая строка несёт собственный подстатус: назначена / зарезервирована / собрана / отправлена / отменена с указанием точки отмены.

### 2.8 Учёт остатков, резервирование и ATP

По каждой паре SKU × склад ядро хранит четыре числа: учётный остаток, физический остаток, резерв и товар в пути с датами прихода. Политики и ATP видят только учётный остаток; физический проявляется на сборке.

**Резервирование** — параметр `reservation: on | off`.

- `on`: при решении sourcing единицы переходят в резерв, ATP других заказов их не видит.
- `off`: остаток списывается только на pick; несколько заказов могут претендовать на одну единицу, конфликт обнаруживается на сборке (третья точка в 2.9). Так ведут себя OMS без онлайн-резервов и сети с запаздывающей синхронизацией остатков.

**ATP (available-to-promise)** — стратегия `atp.method`:

- `on_hand_only`: ATP = учётный остаток − резерв.
- `basic` (по умолчанию): ATP = учётный остаток − резерв − страховой запас.
- `cumulative` (типичная формула с горизонтом): к `basic` прибавляются приходы, ожидаемые до конца горизонта промиса, и вычитаются обещания, уже сделанные на этот горизонт.

```latex
ATP_{w,s}(t) = I_{w,s} - R_{w,s} - SS_{w,s} + \sum_{\tau \le t + H} Q^{in}_{w,s}(\tau) - \sum_{\tau \le t + H} Q^{promised}_{w,s}(\tau)
```

ATP сети по строке = сумма ATP складов, попадающих в допуск `atp.tolerance`: максимальная цена доставки относительно самого дешёвого варианта и максимальный срок относительно промиса. ATP «говорит нет», если строка не покрывается ни одним складом или покрывается только за пределами допуска — это два разных исхода в метриках.

**Точность учёта остатков** — параметр `inventory_accuracy` ∈ \[0; 1\], по умолчанию 1,0 (учёт точный). При каждом приходе на склад с вероятностью 1 − accuracy запись получает скрытую ошибку: физический остаток меньше учётного на величину, распределённую геометрически (среднее `error_mean`, по умолчанию 2). Пока остаток велик, ошибка незаметна; когда учётный остаток опускается до размера ошибки, на сборке оказывается, что товара физически нет. Ошибка обнаруживается на pick, после чего учётный остаток сверяется с физическим. Отдельный RNG-поток `inventory_error`.

### 2.9 Стратегии при нехватке товара

Три точки различаются тем, где находится клиент: на кассе он ещё здесь и может согласиться на замену, после заказа он ушёл довольным — и отмена бьёт сильнее. Все вероятности разыгрываются из потока `customer_choice`; штрафы по точкам задаются в конфиге раздельно.

| Точка | Когда срабатывает | Параметры стратегии | Исходы |
| --- | --- | --- | --- |
| 1. На кассе (`checkout_shortage`) | ATP не покрывает строку: нет нигде, либо только вне допуска по цене или сроку | `p_partial` — доля клиентов, согласных на частичный заказ; `p_substitute` — согласных на замену SKU той же категории с ATP; `p_accept_slow` — согласных на доставку вне допуска; 0 везде → отказ | заказ создан полностью / частично / с заменой; заказ не создан (отказ) |
| 2. После заказа (`post_order_shortage`) | заказ принят, но политика sourcing не нашла назначение строке: запас ушёл между кассой и sourcing (без резерва), политика ограничена допуском | `p_partial_ship` — отправить, что есть, остальное отменить; иначе отменить заказ целиком; `p_substitute_contact` — доля клиентов, принявших замену после контакта (по умолчанию 0) | частичная отправка / отмена заказа; штраф `penalty_post_order` выше, чем на кассе |
| 3. На сборке (`pick_shortage`) | физический остаток меньше учётного (точность учёта) или конфликт заказов без резервирования | `p_resource` — пере-сорсинг строки с другого склада отдельной посылкой; `p_partial_ship`; иначе отмена строки; учётный остаток корректируется | новая посылка / частичная отправка / отмена строки; штраф `penalty_pick` |

Бэкордер остаётся опцией для точек 2 и 3: при `backorder: on` строка ждёт прихода вместо отмены, если приход ожидается внутри допуска по сроку.

### 2.10 Расчёт срока доставки (promise) и отложенный sourcing

Промис — не константа по зоне, а результат стратегии `promise.method`; запас, заложенный в промис, — ресурс, который sourcing может потратить на ожидание прихода недостающего товара. Заказ собирается не раньше минимального времени обработки, но если готов раньше срока — отправляется сразу.

**Стратегия промиса**

| Метод | Обещанная дата | Когда уместен |
| --- | --- | --- |
| `zone_fixed` | дата заказа + дни зоны (2.6) | эталон, простые OMS |
| `atp_based` | самая ранняя дата, к которой все строки доступны по cumulative ATP (с учётом ожидаемых приходов) + минимальная обработка + срок зоны | «честный» промис по запасам |
| `atp_plus_buffer` | `atp_based` + `promise.buffer_days` (0, 1, 2 …) | промис с запасом, даёт sourcing свободу |
| `percentile` | квантиль p фактического срока по зоне за скользящее окно (например, p90) | статистический промис без знания запасов |

Общие параметры: округление до дня; `promise.min_processing` — раньше этого обещать нельзя; `promise.cap_days` — выше промис не выдаётся, строка считается «вне допуска по сроку» (2.8). Чтобы метод с большим запасом не выигрывал бесплатно, вводится отклик клиента `p_accept_promise(d)`: вероятность принять промис в d дней, по умолчанию 1 при d не больше срока зоны и линейно до 0 при `cap_days`; отказ попадает в `checkout_outcomes` как «отказ из-за срока».

**Запас по сроку (slack)** для заказа = промис − (сейчас + минимальная обработка + срок зоны с выбранного склада). Это бюджет ожидания, из которого вычитается `safety_margin` (по умолчанию 0,5 дня); остаток — дедлайн начала сборки.

**Отложенный sourcing** — параметр `sourcing.deferral`:

- `none`: решение сразу после ожидания sourcing (как в базовой схеме).
- `wait_for_receipt`: если полное назначение невозможно без разбиения или отмены, а по cumulative ATP приход закрывает дефицит до дедлайна, политика возвращает `Defer(until = min(дата прихода, дедлайн))`. Ядро пересматривает заказ по событиям: приход на склад, отмена, дедлайн.
- `wait_to_consolidate`: ждать до `max_hold` или дедлайна, чтобы собрать заказ с одного склада и избежать разбиения.
- По дедлайну решение принимается с тем, что есть: разбиение, частичная отправка или стратегия «после заказа» (2.9).

**Арбитраж при приходе товара.** Отложенные заказы не держат резервов: пока заказ в состоянии «Отложен по SLA», ни одна его строка не зарезервирована, резерв ставится атомарно на все строки сразу в момент пробуждения. Иначе заказ, ждущий SKU-A и SKU-B, заблокировал бы пришедший SKU-A для заказа, которому нужен только он, — классический тупик, который лавиной срывает промисы. Правило на событии `receipt`:

- Ядро собирает очередь отложенных заказов, которым нужен пришедший SKU на этом складе, и сортирует её по `deferral.arbitration`: `edf` (по умолчанию — раньше всех тот, у кого меньше запас по сроку), `fifo` (по времени заказа), `value` (по марже заказа).
- По очереди пробует атомарный резерв всех строк заказа; получилось — заказ идёт в «Решение sourcing», нет — остаётся ждать, приход достаётся следующему.
- Обработчик `receipt` выполняется раньше новых заказов с той же меткой времени (приоритет типа события в 6.1), поэтому ожидающие не проигрывают только что пришедшим.
- `deferral.max_waiting_per_sku` — лимит числа ожидающих на SKU×склад; сверх лимита новые заказы не откладываются, а решаются сразу.

Инвариант: у заказа в состоянии «Отложен по SLA» резерв равен нулю (проверяется в `validate`).

Сборка и отправка: обработка начинается, как только все строки назначены (и зарезервированы, если резерв включён); готовый заказ отгружается сразу (`ship_when_ready: true` по умолчанию) либо держится до плановой даты (`ship_at_latest`, для батчинга перевозчика). Ранняя доставка штрафов не снижает, но видна в план-факте.

Риск стратегии: приход запаздывает (стохастический lead time, fill rate < 1) — отложенный заказ срывает промис или уходит в стратегию 2. Такой срыв штрафуется сильнее обычного опоздания: `penalty_deferral_miss` — множитель к штрафу за день опоздания (по умолчанию 2,0), потому что промис был выдан с опорой на ожидаемый приход и сеть сама выбрала ждать. Если по дедлайну приход так и не состоялся и заказ уходит в стратегию 2, применяется `penalty_post_order` с тем же множителем. Оба штрафа входят в `disappointment_cost` и считаются отдельной строкой в `deferral_outcomes`.

## 3. Политики пополнения складов

Пополнение — отдельный плагин с тем же интерфейсом, что и sourcing: политика получает состояние (запас, в пути, история спроса, прогноз) и возвращает список закупок «SKU, склад, поставщик, количество». В экспериментах по sourcing пополнение фиксируется, чтобы сравнивать только выбор склада; в экспериментах по пополнению — наоборот.

| Политика | Правило | Параметры | Зачем в наборе |
| --- | --- | --- | --- |
| `base_stock` | довести запас + в пути до S, пересмотр раз в R дней | S по SKU×склад (или через целевой уровень сервиса), R | простейший эталон |
| `s_S` | если запас + в пути < s, заказать до S | s, S | классика, порождает партии |
| `R_Q` | раз в R дней заказывать Q, если ниже точки заказа | R, Q, reorder point | как у Wang & Minner (2024) |
| `forecast_driven` | S = прогноз спроса на lead time + страховой запас z·σ | окно прогноза, z, тип прогноза (скользящее среднее / экспоненциальное сглаживание) | реалистичная промышленная схема |
| `network_allocation` | общий заказ сети распределяется между складами пропорционально прогнозу региона (pro rata) или через LP минимизации ожидаемой доставки | доля, метод | связь пополнения и sourcing; аналог Acimovic & Graves (2017) |

Общие правила для всех политик:

- Выбор поставщика: самый дешёвый с учётом MOQ и доступной мощности; при нехватке — следующий. Опционально — разбиение закупки между поставщиками.
- Ограничение ёмкости склада: заказ урезается до свободного места.
- Бэклог поставщика: если `fill_rate` < 1, недопоставленное либо отменяется, либо доезжает со следующей партией (флаг).
- Начальный запас задаётся генератором так, чтобы покрыть `initial_cover_days` дней спроса (по умолчанию 14), чтобы не было «холодного старта»; плюс период разогрева (раздел 6).

## 4. Алгоритмы выбора склада (sourcing policies)

Набор покрывает четыре семейства из обзора литературы: простые правила, взвешенная оценка (промышленный эталон), LP/двойственные методы, ML/RL. Плюс две границы — hindsight-оптимум сверху и случайный выбор снизу.

### 4.1 Интерфейс политики

Политика реализует `decide(order, state) -> Assignment`, где `state` содержит: учётный остаток, резерв, ATP и в пути по SKU×склад (физический остаток политике не виден, 2.8), загрузку складов на сегодня и в очереди, тарифы и сроки по зонам, текущее время, промис заказа, и (по флагу) прогноз спроса на горизонт. Опционально — `on_period_start(state)` для пересчёта двойственных цен и `fit(history)` для обучаемых политик. Решение должно укладываться в бюджет времени (параметр, по умолчанию 50 мс/заказ, только для логирования).

Если включён отложенный sourcing (2.10), `decide()` может вернуть `Defer(until, reason)` вместо назначения; ядро вызовет политику снова по приходу товара на склад или по дедлайну. В `state` для этого есть расписание ожидаемых приходов и запас по сроку текущего заказа.

### 4.2 Набор политик v1

| Семейство | Политика | Правило | Ссылка на литературу |
| --- | --- | --- | --- |
| Границы | `random` | случайный склад с запасом | нижняя граница |
| Границы | `hindsight_lp` | LP по всему горизонту с известным будущим спросом | верхняя граница, как у Acimovic & Graves (2015) |
| Правила | `nearest` | ближайший склад, где есть все строки; иначе минимум посылок | базовая у Shelke et al. (2023) |
| Правила | `cheapest_myopic` | минимизирует текущую стоимость доставки + обработки, разбиение разрешено | myopic у Jasin & Sinha (2015), DeValve et al. (2023) |
| Правила | `weighted_score` | оценка = Σ wᵢ · нормированный факторᵢ по кандидатам; факторы: расстояние, цена доставки, срок vs промис, число разбиений, запас выше страхового, загрузка склада, ранг склада | промышленный эталон (Adobe Commerce OMS, патент US 10 839 338) |
| Правила | `weighted_score_tuned` | те же факторы, веса подобраны Bayesian optimization / CMA-ES на тренировочных сидах | «ML-light» линия, вклад статьи |
| LP | `dtlp_bidprice` | раз в период решается транспортная LP на прогноз; двойственные цены = альтернативная стоимость единицы запаса; заказ идёт туда, где доставка + Σ dual минимальна | Acimovic & Graves (2015), DTLP у Ye et al. (2026) |
| LP | `primal_dual` | онлайн primal-dual без прогноза, множители обновляются по факту расхода | Andrews et al. (2019) |
| LP | `spillover_limit` | myopic с лимитом доли «чужих» заказов на склад | DeValve et al. (2023) |
| LP | `rolling_milp` | каждые T минут MILP по накопленным заказам (батчинг) с ограничениями мощности | аналог переоптимизации Xu et al. (2009) |
| ML | `learned_scorer` | градиентный бустинг / MLP предсказывает «стоимость до конца горизонта» назначения, обучен на журналах `hindsight_lp` | аналог Wang & Minner (2024), Ye et al. (2026) |
| RL | `ppo` | PPO в Gymnasium-обёртке: наблюдение — вектор по складам-кандидатам, действие — склад или разбиение по правилу | Wang & Minner (2024) |
| RL | `dqn` | DQN с тем же наблюдением | Shelke et al. (2023) |

### 4.3 Обработка многотоварных заказов

- Кандидаты: все склады с запасом хотя бы одной строки; полный перебор назначений ограничен топ-k складами (k = 4 по умолчанию) и жадным дополнением для остальных строк.
- Штраф за разбиение входит в стоимость как фиксированная плата за дополнительную посылку плюс её реальный тариф.
- Если политика не может назначить строку (нет запаса или только вне допуска), срабатывает стратегия «после заказа» из 2.9: частичная отправка с вероятностью p\_partial\_ship, иначе отмена со штрафом упущенной продажи; бэкордер — опциональный сценарий.

### 4.4 Взвешенная оценка — детали

```latex
score_w(o) = \sum_i w_i \cdot f_i(w, o), \qquad f_i \in [0,1],\ \sum_i w_i = 1
```

Факторы нормируются по кандидатам текущего заказа (min–max), чтобы веса были сравнимы между сценариями. Срок vs промис — бинарный фактор «успеваем / не успеваем» плюс линейная добавка за запас по дням. Набор весов по умолчанию и диапазоны для калибровки хранятся в конфиге политики.

### 4.5 Обучаемые политики — протокол

- Обучение только на сидах 0–9 (train), выбор гиперпараметров на 10–14 (val), отчёт по 15–44 (test). Тестовые сиды никогда не используются для настройки.
- Для RL: награда = −(доставка + обработка + штраф за опоздание + штраф за разбиение) за заказ; эпизод = один день; фиксируем время обучения в часах GPU/CPU.
- Робастность: обученные на `medium` политики дополнительно тестируются на сценариях со сдвигом спроса и выпадением склада без переобучения.

### 4.6 Пространство действий RL

Прямое назначение K строк на M складов даёт порядка M^K действий; PPO и DQN «из коробки» на таком пространстве проигрывают жадным правилам. Поэтому:

- Декомпозиция по строкам: заказ обрабатывается как последовательность решений «строка → склад» с маскированием недопустимых действий (нет запаса, нет мощности); в состояние входят уже сделанные назначения.
- Альтернативная формулировка для сравнения: агент выбирает основной склад заказа, остальные строки дополняются жадно — тот же приём, что в `weighted_score`.
- Обязательный анализ в статье: кривые обучения, разброс по сидам обучения, сравнение с `weighted_score_tuned` при равном бюджете вычислений. Таблица «RL проиграл» без анализа причин в статью не идёт.

### 4.7 Масштабируемость LP-политик

- `dtlp_bidprice`: LP строится на кластерах SKU по оборачиваемости (50–200 кластеров) × склады × регионы, пересчёт раз в 4 часа; порядка 10⁵ переменных, HiGHS решает за секунды.
- `rolling_milp`: полноценно — только на `tiny`/`small` и на выборочных окнах `medium`; на полном `medium`/`large` заменяется LP-релаксацией с округлением.
- `hindsight_lp` на `medium` решается один раз на сид по кластерам SKU и хранится в кэше.
- Бюджет времени на политику задаётся в конфиге эксперимента; политики, не уложившиеся, помечаются в таблицах, а не исключаются.

Главный показатель — полная стоимость на заказ за горизонт после разогрева; остальные метрики объясняют, из чего она складывается. Все метрики считаются из журнала событий постфактум, а не внутри политик, чтобы политики нельзя было «подкрутить» под метрику.

**Метрики промиса и отложенного sourcing (2.10)**

| Метрика | Определение |
| --- | --- |
| `promise_length_days` | распределение выданного промиса по зонам и методам |
| `promise_rejections` | доля отказов на кассе из-за длинного промиса |
| `slack_days` | выданный и фактически использованный запас по сроку |
| `deferred_share` | доля заказов, прошедших через «Отложен по SLA» |
| `deferral_outcomes` | исходы отложенных: дождался прихода и собран одним складом / дождался, но разбит / дедлайн без прихода → стратегия 2 |
| `splits_avoided_by_deferral` | разбиения, которых удалось избежать ожиданием (сравнение с мгновенным решением на том же состоянии) |
| `earliness_days` | на сколько дней раньше промиса доставлено; p50, p90 |
| `promise_hit_rate_by_method` | план-факт доставки (выше) в разрезе метода промиса и буфера |

**План-факт по доставке.** Для каждой посылки пишется: обещанная дата, дата по тарифу на момент решения, фактическая дата. Три величины дают две матрицы: «обещали × доставили» и «политика рассчитывала × вышло». Каждый день опоздания раскладывается по источнику: пропуск cut-off из-за времени сборки (внутренняя задержка склада), очередь по мощности склада, очередь перевозчика, ожидание прихода при отложенном sourcing, шум доставки. Матрица «политика рассчитывала × вышло» строится отдельно по каждому источнику; при нулевом шуме доставки в ней остаются только внутренние задержки — удобная проверка корректности.

**Разрезы.** Все метрики доступны по дню, по складу, по региону, по зоне доставки, по категории SKU и по типу дня (обычный / пик / после сбоя).

## 6. Воспроизводимость и протокол сравнения

Любые две политики на одном сиде видят один и тот же мир: те же клиенты, те же заказы в те же минуты, те же сроки поставок. Это требование к архитектуре, а не к дисциплине экспериментатора.

### 6.1 Общие случайные числа (CRN)

- Один мастер-сид → `numpy.random.SeedSequence.spawn()` → независимые потоки с фиксированными именами: `geo` (регионы, склады), `catalog` (SKU, поставщики), `demand_arrivals`, `demand_basket`, `supplier_leadtime`, `supplier_fill`, `shocks`, `delivery_noise`, `process_times` (ожидания в состояниях заказа), `inventory_error` (ошибки учёта), `customer_choice` (решения клиентов при нехватке), `policy` (внутренняя случайность политики).
- Поток спроса генерируется заранее на весь горизонт в виде таблицы заказов и сохраняется в parquet; политики читают один файл. Так никакое ветвление в решениях не сдвигает поток случайных чисел.
- Потоки, которые опрашиваются только при определённых событиях, не могут быть последовательными: политика A выполнила заказ сразу и не трогала customer\_choice, политика B на том же заказе испытала дефицит и сделала вызов — на следующем дефицитном заказе они получили бы разные числа, и CRN разъехался бы. Поэтому customer\_choice, inventory\_error, process\_times, delivery\_noise и supplier\_leadtime реализованы как counter-based (stateless) генераторы: значение = hash(master\_seed, имя потока, ключ события), где ключ — (order\_id, line\_id, stage) для решений клиента и времён обработки, (sku, warehouse, receipt\_index) для ошибок учёта, (order\_id, parcel\_index) для шума доставки, (supplier, warehouse, po\_index) для сроков поставки. Реализация — numpy Philox с ключом из хеша; один и тот же заказ при любой политике получает одно и то же число.
- Случайность внутри политики (RL, рандомизированное округление) — только из потока `policy` с собственным сидом, который перебирается отдельно.
- Детерминизм: события с одинаковым временем упорядочиваются по (время, приоритет типа, порядковый номер). Многопоточность — только между репликациями, никогда внутри прогона.

### 6.2 Протокол эксперимента

1. Сценарий = YAML-конфиг + список сидов. Хеш конфига входит в имя результата.
2. Разогрев: первые 14 дней не входят в метрики (параметр `warmup_days`).
3. Репликации: 30 сидов на сценарий для основных таблиц, 10 — для сеток чувствительности.
4. Сравнение политик — парное: разность метрики по сиду, затем среднее и 95 % доверительный интервал по t-распределению; дополнительно бутстреп (10 000 выборок).
5. Сетка чувствительности: нагрузка сети (спрос / мощность ∈ {0,6; 0,8; 0,95; 1,1}), покрытие запасом (дни ∈ {7; 14; 30}), доля многотоварных заказов, крутизна тарифа по расстоянию, промис по зонам (базовый / ужесточённый на 1 день), шум доставки (0 / умеренный / сильный), резервирование (вкл / выкл), точность учёта (1,0 / 0,98 / 0,95), метод промиса и буфер (zone\_fixed / atp\_based / atp\_plus\_buffer на 1–2 дня) × отложенный sourcing (none / wait\_for\_receipt).
6. Каждый прогон пишет `manifest.json`: версия кода (git-хеш), версия конфига, сиды, версии библиотек, время запуска, машина.

### 6.3 Проверка воспроизводимости

- «Золотой прогон»: для пресета `small` и сида 0 в репозитории хранятся контрольные суммы журнала событий; CI сравнивает побайтово.
- Два прогона с одним конфигом и сидом на разных машинах должны давать идентичные метрики с точностью до 1e-9.

## 7. Архитектура ПО и интерфейс командной строки

Стенд — Python-пакет `osbench` с одним ядром симуляции и тремя слоями вокруг него: генерация сценария, плагины политик, отчёты. Ядро не знает о визуализации: оно только пишет журнал событий, а отчёты и просмотрщик читают журнал постфактум.

&#91;embedded content: архитектура osbench · 9 компонентов, один журнал\]

Данные текут сверху вниз: конфиг и сид порождают мир, ядро с подключёнными политиками пишет журнал, а три инструмента справа и слева читают только журнал — поэтому их можно переписывать, не трогая симуляцию.

### 7.1 Компоненты

| Компонент | Ответственность | Вход → выход |
| --- | --- | --- |
| `config` | схемы pydantic для сценария, политик, эксперимента; валидация YAML; пресеты | YAML → объекты конфигурации |
| `generate` | генератор мира (регионы, склады, SKU, поставщики) и предгенератор спроса | конфиг + сид → `world.parquet`, `orders.parquet` |
| `core` | цикл событий, состояние запасов, очереди складов и перевозчика, календарь | мир + политики → журнал событий |
| `policies.sourcing` | плагины выбора склада (раздел 4), реестр через entry points | заказ + состояние → назначение |
| `policies.replenishment` | плагины пополнения (раздел 3) | состояние → закупки |
| `metrics` | расчёт метрик из журнала, парные сравнения, бутстреп | журнал → `metrics.json`, `compare.csv` |
| `reports` | статические HTML-отчёты (Plotly, без сервера) | метрики → `report.html` |
| `replay` | просмотрщик прогона: карта и временная шкала из журнала | журнал → `replay.html` |
| `rl` | Gymnasium-обёртка над ядром, скрипты обучения PPO/DQN | ядро → среда |
| `cli` | команды на Typer | — |

### 7.2 Команды

```bash
osbench generate --config scenarios/medium.yaml --seed 0 --out runs/medium_s0/
osbench run --scenario runs/medium_s0/ --sourcing weighted_score --replenishment forecast_driven --out runs/medium_s0/ws/
osbench sweep --config experiments/main.yaml            # сетка сценариев × политик × сидов, параллельно по процессам
osbench compare runs/medium_s*/{ws,dtlp,ppo}/ --baseline ws --out compare/
osbench report runs/medium_s0/ws/ --open               # статический HTML-отчёт по одному прогону
osbench replay runs/medium_s0/ws/ --speed 60 --open    # интерактивный просмотр
osbench train ppo --config rl/ppo_small.yaml --seeds 0-9
osbench validate runs/medium_s0/ws/                    # инварианты и золотой прогон
osbench run --scenario runs/medium_s0/ --sourcing ppo --live --baseline runs/medium_s0/ws/ --serve   # живой мониторинг против эталона
osbench resume runs/medium_s0/ppo/                     # продолжить с последнего чекпоинта
```

Каждая команда завершает работу кодом 0/1 и пишет JSON-резюме в stdout при флаге `--json` — для CI и скриптов.

### 7.3 Форматы данных

- `world.parquet` (таблицы `regions`, `warehouses`, `skus`, `suppliers`, `tariffs`) и `orders.parquet` (строки заказов с временем прихода и регионом) — вход прогона.
- `events.parquet` — журнал: `t, type, order_id, line_id, sku, warehouse, qty, cost, promised_at, planned_at, delivered_at, policy_time_ms`. Один прогон `medium` на 90 дней — порядка 5 млн строк, \~150 МБ.
- `inventory_daily.parquet` — снимок запасов и загрузки по дням (для графиков, чтобы не пересчитывать из журнала); metrics\_live.parquet и checkpoints/ — для живого мониторинга и продолжения прогона (8.4).
- `metrics.json` + `manifest.json` — результат и происхождение.
- Схема журнала версионируется; отчёты проверяют версию.

### 7.4 Производительность

- Цель: пресет `medium` (1,8 млн заказов за 90 дней) с правилом `weighted_score` — не более 5 минут на одном ядре (лимит только для правил; LP-политики — до 30 минут на прогон, RL — отдельный бюджет обучения, раздел 4.6); `sweep` масштабируется по процессам через `multiprocessing`.
- Горячие пути (расчёт кандидатов, тарифов, оценок) — векторизованы в NumPy; при необходимости Numba.
- LP-политики решают LP раз в период, а не на каждый заказ; размер LP ограничен агрегацией SKU в кластеры по скорости оборота.

## 8. Визуализация

Визуализация решает две разные задачи: убедиться, что симулятор работает правильно (просмотр одного прогона), и показать результаты сравнения (отчёты). Обе — статические HTML-файлы на Plotly.js, открываются двойным щелчком, без сервера и без интернета; при желании `--serve` поднимает локальный просмотрщик с живым обновлением во время прогона.

### 8.1 Просмотр прогона (`osbench replay`) — проверка корректности

Одна страница с картой и временной шкалой, синхронизированными ползунком времени.

| Элемент | Что показывает | Что ловит |
| --- | --- | --- |
| Карта сети | склады (размер = запас, цвет = загрузка / мощность), регионы (размер = спрос за день), линии «склад → клиент» для посылок текущего часа, цвет линии = зона тарифа | заказы уходят из странного склада, «дыры» в покрытии, перегруженный склад |
| Анимация пополнений | дуги «поставщик → склад» с посылками в пути | lead time, неправильный MOQ, забытый поставщик |
| Лента событий | хронология одного выбранного заказа: приход → решение → резерв → отгрузка → доставка, с причиной решения (оценки по кандидатам) | политика ведёт себя не так, как задумано |
| Запасы по складу | мелкие графики запас/в пути/дефицит по топ-SKU | дефициты, «пилы» пополнения |
| Очереди | длина очереди обработки и очереди перевозчика по складу | накопление отложенных заказов |
| Панель инвариантов | счётчики из `validate` в реальном времени: баланс запаса, нераспределённые заказы, отрицательные остатки | ошибки ядра |

Для больших прогонов просмотрщик читает журнал кусками по дню; на `tiny`/`small` — целиком.

### 8.2 Отчёт по прогону (`osbench report`)

- Стоимость на заказ по дням с разбивкой на компоненты (stacked area); вертикальные метки шоков из конфига.
- План-факт доставки: гистограмма (факт − обещание) в днях; тепловая карта «обещано × доставлено»; доля опозданий по зоне и региону на карте.
- Разбиения: доля заказов из 1 / 2 / 3+ посылок по дням.
- Загрузка складов и перевозчика: тепловая карта «склад × день», порог 100 % выделен.
- Запасы: дни покрытия по складу; доля SKU в дефиците по дням.
- Распределение времени решения на заказ.

### 8.3 Сравнение политик (`osbench compare`)

- Главная таблица: политика × метрика, среднее по сидам и 95 % парный ДИ к базовой (`weighted_score`); красным — хуже базовой статистически значимо, зелёным — лучше.
- Разброс по сидам: точки по сидам для каждой политики, соединённые линиями — видно, что CRN работает (политики «ходят вместе» по сидам).
- Чувствительность: сетка «нагрузка × покрытие запасом», в ячейке — лучшая политика и её выигрыш к базовой в процентах.
- Фронт Парето «стоимость на заказ × доля вовремя»: точка на политику с усами по сидам.
- Стоимость против времени решения: где RL и LP платят вычислениями.
- Робастность: столбцы «выигрыш на train-сценариях» vs «на сценариях со сдвигом».

Все графики отчётов также экспортируются в PNG/PDF (`--export`) и в CSV с данными графика — для статьи.

### 8.4 Живой мониторинг и ранняя остановка (`osbench run --live`, `sweep --live`)

Цель — увидеть за первые минуты, что прогон идёт не туда, и остановить его раньше, чем он сожжёт часы вычислений. Ключевой приём: благодаря CRN текущий прогон можно сравнивать с уже сохранённым эталонным прогоном на том же сиде день в день.

**Как это работает**

- Ядро раз в N симулированных часов (по умолчанию 6) дописывает снапшот в `metrics_live.parquet`: скользящие метрики за окно, инварианты, время решения, прогресс.
- Та же страница, что и `replay`, в режиме live автообновляется из хвоста файла (`--serve` поднимает локальный просмотрщик; без него — статический HTML, который перерисовывается при каждом снапшоте).
- Если в папке эксперимента есть эталонный прогон на том же сиде (`--baseline`), все графики рисуются парой «текущий / эталон» и разностью.

**Что видно по ходу прогона**

| Панель | Содержание | Сигнал «не туда» |
| --- | --- | --- |
| Стоимость на заказ | скользящее среднее за 24 ч, компоненты, линия эталона | устойчиво выше эталона после прогрева |
| Сервис | доля вовремя, lost sales, бэкордеры | провал без шока в конфиге |
| Сеть | split rate, загрузка складов и перевозчика, длина очередей | очередь растёт монотонно |
| Запасы | доля SKU в дефиците, дни покрытия по складу | дефицит растёт при нормальном спросе — пополнение сломано |
| Вычисления | p50/p99 времени решения, прогноз времени до конца прогона | p99 выше бюджета, прогноз — часы вместо минут |
| Инварианты | счётчики нарушений в реальном времени | любое ненулевое значение |
| Sweep | таблица «сид × политика»: прогресс, текущая стоимость, отклонение от эталона цветом | целый столбец политики красный |
| Обучение RL | награда и доля опозданий на валидации по эпохам | плато или деградация |

**Правила ранней остановки (guardrails в конфиге эксперимента)**

- Нарушение инварианта (включая ненулевой резерв у отложенного заказа) → немедленная остановка, статус `failed`.
- После прогрева: стоимость на заказ хуже эталона более чем на X % (по умолчанию 25 %) в течение Y дней подряд (по умолчанию 7) → остановка со статусом `aborted`; режим `warn` вместо `stop` — по флагу.
- Доля lost sales или очередь склада выше порога; p99 времени решения выше бюджета политики.
- Для RL: нет улучшения на валидации за K эпох.
- В `sweep`: политика, остановленная на 3 сидах подряд, снимается с оставшихся сидов, остальные политики продолжаются.

Каждые N дней ядро сохраняет чекпоинт состояния; `osbench resume` продолжает прогон с него. Ctrl+C сохраняет чекпоинт и частичные метрики, а не теряет прогон. Остановленные прогоны попадают в `compare` с пометкой, а не исчезают.

## 9. Тестирование и критерии приёмки

Стенд считается принятым, когда все инварианты выполняются на всех пресетах, золотой прогон воспроизводится побайтово и эталонные политики ведут себя так, как предсказывает теория.

### 9.1 Инварианты ядра (проверяются в `validate` и в CI)

- Баланс запаса по каждому SKU×склад: начальный + приход − отгрузка − списание = конечный, на каждый день.
- Нет отрицательных учётных и физических остатков; резерв не превышает учётный остаток; отгружено ≤ физического остатка и без резервирования тоже; после каждой сверки на pick учётный остаток равен физическому.
- Каждая строка заказа заканчивается ровно одним из состояний: доставлена / отменена (с точкой отмены: касса, после заказа, сборка) / бэкордер закрыт; переходы между состояниями — только по рёбрам машины состояний 2.7, время в каждом состоянии ≥ 0.
- Отгрузки за день со склада ≤ мощности; посылки за день ≤ мощности перевозчика.
- `delivered_at − shipped_at` равно тарифному сроку зоны при `delivery_noise_days = 0`.
- Сумма компонент стоимости = полная стоимость.

### 9.2 Проверки правдоподобия (sanity checks на `small`)

| Проверка | Ожидание |
| --- | --- |
| `random` vs `nearest` | `nearest` дешевле по доставке на 20 % и более |
| `cheapest_myopic` при избытке запаса (покрытие 30 дней) | не хуже `dtlp_bidprice` в пределах ДИ |
| `cheapest_myopic` при дефиците (покрытие 7 дней, нагрузка 0,95) | хуже `dtlp_bidprice` статистически значимо |
| `hindsight_lp` | не дороже любой другой политики на каждом сиде |
| Двойной спрос | стоимость на заказ растёт, доля вовремя падает, загрузка складов > 100 % в пик |
| Выпадение склада | заказы его региона уходят соседям, опоздания растут в зоне, запас соседей падает |
| Отключение CRN (разные сиды спроса для двух политик) | разброс парной разности растёт заметно — демонстрация пользы CRN |

### 9.3 Критерии приёмки

- [ ] `pytest` — инварианты на `tiny` и `small`, покрытие ядра ≥ 85 %.
- [ ] Золотой прогон `small`/сид 0 воспроизводится на Linux и macOS.
- [ ] Все 13 политик раздела 4 запускаются одной командой `sweep` на `medium` с 30 сидами и дают `compare.csv`.
- [ ] `medium`/`weighted_score`: 90 дней ≤ 5 минут на одном ядре.
- [ ] `replay` открывает прогон `small` и воспроизводит хронологию любого заказа; режим --live показывает первые метрики не позже чем через 60 с после старта medium и останавливает прогон с заведомо сломанной политикой (например, с отрицательными весами) по guardrail, а не по таймеру.
- [ ] Документация: README с примером за 5 минут, описание схемы конфигов и журнала, инструкция по добавлению политики (один файл + регистрация).

## 10. Этапы разработки и открытые вопросы

Разработка идёт в пять этапов; каждый закрывается проверяемым результатом, и уже после второго этапа можно получать первые сравнения.

1. **Ядро и генератор (MVP).** Конфиги, генератор мира и спроса, цикл событий, склады с мощностью и cut-off, детерминированная почта, `base_stock`, политики `random` / `nearest` / `cheapest_myopic`, журнал, инварианты. Гейт: золотой прогон `small` и все инварианты зелёные.
2. **Метрики, сравнение, отчёт.** `metrics`, парные ДИ, `compare`, `report`, `sweep`. Гейт: таблица сравнения трёх политик на 30 сидах с ДИ.
3. **Полный набор правил и LP.** `weighted_score` (+ калибровка весов), `dtlp_bidprice`, `primal_dual`, `spillover_limit`, `rolling_milp`, `hindsight_lp`; политики пополнения `s_S`, `R_Q`, `forecast_driven`, `network_allocation`. Гейт: проверки правдоподобия 9.2 проходят.
4. **Просмотрщик и валидация.** `replay` с картой и хронологией заказа, панель инвариантов, `validate`. Гейт: сторонний разработчик находит подброшенную ошибку в политике через просмотрщик.
5. **ML/RL и статья.** Gymnasium-обёртка, `learned_scorer`, `ppo`, `dqn`, протокол train/val/test, робастность, ускорение прогонов при необходимости. Гейт: полная сетка экспериментов `medium` и черновик результатов.

### Открытые вопросы

Решено по итогам рецензии:

- География — реальные координаты и население агломераций (2.1).
- Неудовлетворённая строка — упущенная продажа; бэкордеры опционально (4.3).
- Тарифы — синтетические, в условных единицах: монотонная функция расстояния с настраиваемой крутизной (2.3); привязка к реальному оператору не нужна.
- Промис — по зонам (2.6).
